# 이공계 연구생활장려금 관리시스템 — 프로젝트 회고

## 1. 프로젝트 개요

본 프로젝트는 동국대학교 「nDRIMS 이공계 연구생활장려금 지원사업 전산시스템 구축 사업」 제안요청서(RFP)를 바탕으로, 대학원생의 연구생활장려금 지급 및 관리 업무를 지원하는 웹 시스템을 구현하는 것을 목표로 진행하였다.

단순히 화면을 만드는 것에 그치지 않고, 학적·지급·회계 데이터를 연동하고 지원 대상 여부와 지급 금액을 검증하며, 사용자 권한에 따라 정보 접근을 제한하는 업무 시스템의 전반적인 구조를 경험하고자 하였다.

개발에는 Next.js, TypeScript, Drizzle ORM, SQLite 등을 활용하였으며, 최종적으로 Vercel과 Turso를 이용하여 실제 웹 서비스를 배포하였다.

- GitHub: https://github.com/euhn5/stipend-mentoring
- 배포 주소: https://stipend-mentoring.vercel.app

## 2. 구현 범위 및 결과

### 2-1. 주요 구현 기능

**① 학적 연동 및 지원 대상 판정**

학생의 학적 정보와 연구 관련 데이터를 바탕으로 지원 대상 여부를 판정하는 기능을 구현하였다. 전일제 여부나 휴학 상태 등 지원 요건에 영향을 미치는 조건을 검사하고, 연동 결과를 화면에서 확인할 수 있도록 하였다.

**② 지급 내역 연동 및 검증**

학생별 연구생활장려금 지급 정보를 연동하고, 지급 계획과 실제 지급액을 비교하는 기능을 구현하였다. 원천 데이터에 필수값 누락이나 잘못된 코드가 포함된 경우 오류를 검출하고, 정상 데이터와 구분해 처리하도록 하였다.

**③ 기관계정 연동 및 정합성 검사**

기관계정의 수입·지출 내역을 연동하고 잔액을 확인하는 기능을 구현하였다. 원장 데이터와 집계 결과가 일치하는지 검사하여 회계 데이터의 정합성을 확인할 수 있도록 하였다.

**④ 사용자별 접근 권한 관리**

관리자와 교수 계정을 구분하고, 교수는 자신이 담당하는 학생의 정보만 조회할 수 있도록 권한을 제한하였다. 화면에서 메뉴를 숨기는 것뿐 아니라 다른 교수의 학생 상세 URL에 직접 접근하는 경우도 차단되는지 확인하였다.

**⑤ 감사로그 기록**

지급 계획을 생성하거나 수정하는 과정에서 변경 전후의 값과 작업자 정보를 기록하는 감사로그 기능을 구현하였다. 이를 통해 데이터가 변경된 이력을 추적할 수 있도록 하였다.

**⑥ 자동 연동 API**

학적·지급·회계 데이터를 순차적으로 처리하는 자동 연동 API를 구현하고, Vercel Cron을 이용해 매월 정기 실행되도록 설정하였다. 인증되지 않은 호출을 차단하고, 필요한 원천 데이터가 존재하지 않을 경우 연동을 건너뛰도록 하였다.

### 2-2. 검증 결과

운영 환경에서 관리자와 교수 계정의 로그인 및 주요 화면 접근을 확인하였고, 학적·지급·회계 연동을 직접 실행하여 결과를 검증하였다.

또한 Vitest 테스트 90개가 통과하였으며, TypeScript 검사와 Next.js 운영용 빌드에도 성공하였다. 운영 의존성 보안 검사에서는 취약점이 발견되지 않았다.

다만 Cron의 실제 예약 실행은 아직 확인하지 못했으며, 전체 API에 대한 종합적인 보안 점검도 추가로 필요하다.

## 3. 요구사항 해석 과정

이번 프로젝트에서 중요했던 부분은 제안요청서에 작성된 업무 요구사항을 구체적인 프로그램 동작으로 바꾸는 과정이었다.

예를 들어 '지원 대상 여부를 확인한다'는 요구사항은 단순히 학생 목록을 보여주는 기능이 아니라, 어떤 학적 상태를 지원 대상으로 인정할지 정하고 이를 판정하는 규칙을 구현해야 한다는 의미였다.

또한 '지급 내역의 정합성을 확인한다'는 요구사항을 구현하기 위해서는 지급 계획과 실제 지급액을 구분하고, 잘못된 원천 데이터가 들어왔을 때 어떤 오류를 반환해야 하는지도 정해야 했다.

이 과정에서 요구사항 문서의 판정 기준과 인수 시나리오를 참고하여 구현 내용을 결정하였다. 기능을 먼저 만든 뒤 결과를 확인하기보다는, 기대되는 결과를 정의하고 코드와 테스트가 그 결과를 만족하는지 확인하는 방식의 중요성을 배웠다.

## 4. 개발 과정에서 어려웠던 점과 해결 방법

### 4-1. 로컬 데이터베이스와 운영 환경의 차이

처음에는 SQLite 파일을 사용하여 데이터를 저장하였다. 로컬 개발 환경에서는 정상적으로 작동했지만, Vercel의 서버리스 환경에서는 로컬 파일을 지속적으로 저장하고 공유하는 방식에 한계가 있었다.

이를 해결하기 위해 기존 SQLite와 호환되는 Turso를 도입하였다. 기존 Drizzle ORM과 데이터베이스 접근 코드를 최대한 유지하면서 원격 데이터베이스로 전환할 수 있었다.

이 경험을 통해 로컬에서 정상적으로 실행되는 프로그램이 반드시 운영 환경에서도 동일하게 동작하는 것은 아니며, 배포 환경의 특성을 고려한 설계가 필요하다는 점을 이해하였다.

### 4-2. 운영 데이터의 안전한 관리

개발 과정에서는 테스트를 위해 데이터베이스를 초기화하거나 시드 데이터를 삽입하는 작업을 반복하였다. 하지만 운영 데이터베이스에서 동일한 명령을 실행하면 기존 데이터가 손상될 위험이 있었다.

따라서 개발용 초기화 작업과 운영용 데이터 등록 작업을 구분하고, 기존 데이터를 삭제하거나 덮어쓰지 않도록 안전장치를 마련하였다.

이를 통해 기능 구현뿐 아니라 데이터의 보존과 운영 안정성도 중요하다는 사실을 배웠다.

### 4-3. 사용자 권한에 따른 데이터 접근 제한

처음에는 관리자와 교수에게 서로 다른 메뉴를 보여주는 것만으로 권한을 구분할 수 있다고 생각하기 쉬웠다. 그러나 사용자가 URL을 직접 입력하면 화면에 표시되지 않는 페이지에도 접근을 시도할 수 있다는 문제가 있었다.

이를 해결하기 위해 서버 측에서도 사용자 역할과 담당 학생 여부를 검사하도록 구현하였다. 실제로 교수 계정으로 다른 교수의 학생 상세 URL에 접근하여 정보가 노출되지 않는지 확인하였다.

이를 통해 화면의 표시 여부와 실제 데이터 접근 권한은 별도로 검증해야 한다는 점을 이해하였다.

### 4-4. 자동 연동과 예외 처리

자동 연동을 구현하면서 단순히 정해진 시간에 API를 호출하는 것만으로는 충분하지 않다는 사실을 알게 되었다.

인증되지 않은 요청을 차단해야 하고, 처리 대상인 원천 데이터가 없는 경우를 구분해야 하며, 앞선 연동 작업에 실패하면 다음 작업이 잘못된 데이터를 바탕으로 실행되지 않도록 해야 했다.

이에 따라 인증 검사, 원천 데이터 존재 여부 확인, 작업 결과에 따른 후속 실행 중단 처리를 구현하였다.

## 5. AI 도구 활용 경험

이번 프로젝트에서는 생성형 AI를 활용하여 개발 환경 설정, 코드 작성, 오류 분석, 테스트 코드 작성, 배포 과정 등을 학습하고 진행하였다.

특히 처음 접하는 Next.js, Drizzle ORM, Turso, Vercel 등의 기술을 이해하고 적용하는 과정에서 도움을 받았다.

AI가 제안한 코드나 명령어를 그대로 신뢰하기보다는 실제 실행 결과와 오류 메시지를 확인하며 작업을 진행하였다. 예상한 결과와 다른 출력이 나오면 원인을 다시 분석하고, 테스트나 실제 화면을 통해 수정 결과를 검증하였다.

이 과정에서 AI는 개발 속도를 높이고 새로운 기술을 학습하는 데 유용하지만, **생성된 결과의 정확성과 안전성을 최종적으로 확인하는 과정은 개발자가 직접 수행해야 한다**는 점을 배웠다.

또한 한 번에 많은 기능을 구현하기보다 작은 단위로 작업하고, 각 단계의 결과를 확인한 뒤 다음 단계로 넘어가는 방식이 오류를 발견하고 해결하는 데 효과적이었다.

## 6. GitHub 및 호스팅 경험

Git을 이용해 개발 이력을 관리하고 GitHub에 코드를 업로드하였다. 이후 GitHub 저장소를 Vercel과 연결하여 웹 서비스를 배포하였다.

배포 과정에서는 환경변수, 원격 데이터베이스 연결, 운영용 빌드, 사용자 계정 생성 등 로컬 개발과 다른 작업들이 필요했다.

특히 데이터베이스를 Turso로 분리하면서 웹 서버와 데이터 저장소가 서로 독립적으로 운영되는 구조를 경험할 수 있었다.

또한 비밀번호 해싱, 환경변수를 이용한 비밀키 관리, 접근 권한 검사, 자동 연동 API 인증 등을 적용하면서 실제 서비스 운영에 필요한 보안 요소를 학습하였다.

최종적으로 서비스 배포와 주요 기능 검증을 완료하였으며, 자동 연동 일정도 등록하였다. 다만 자동 연동이 실제 예약 시점에 성공적으로 실행되는지는 추후 확인해야 한다.

## 7. 다시 개발한다면 개선하고 싶은 점

프로젝트를 다시 진행한다면 초기 단계부터 데이터베이스의 운영 환경과 배포 구조를 함께 고려하고 싶다. 로컬 데이터베이스로 개발한 뒤 운영 환경으로 전환하는 과정에서 추가 작업이 발생했기 때문이다.

또한 기능을 구현할 때마다 해당 기능의 테스트와 권한 검사를 함께 작성하여, 개발 후반에 검증 작업이 집중되지 않도록 개선하고 싶다.

업무 규칙과 데이터 구조를 먼저 충분히 이해하고 설계한 뒤 구현한다면, 개발 도중 발생하는 수정 작업도 줄일 수 있을 것이라고 생각한다.

마지막으로 새로운 기술이나 AI가 생성한 코드를 사용할 때는 동작 원리를 이해하고 검증하는 과정을 더욱 체계적으로 기록하고 싶다.

## 8. 프로젝트를 통해 배운 점

이번 프로젝트를 통해 웹 개발은 단순히 화면과 기능을 구현하는 작업에 그치지 않는다는 점을 배웠다. 실제 업무 시스템을 만들기 위해서는 요구사항 분석, 데이터 설계, 업무 규칙 구현, 오류 처리, 접근 권한 관리, 테스트, 배포까지 다양한 요소를 함께 고려해야 했다.

특히 처음에는 익숙하지 않았던 기술을 하나씩 학습하면서 실제로 동작하는 서비스를 완성하고, 이를 운영 환경에서 검증하는 경험을 할 수 있었다.

앞으로도 새로운 기술을 사용할 때 구현 결과뿐 아니라 왜 그렇게 설계했는지, 어떤 문제를 해결했는지, 어떻게 검증했는지를 함께 생각하며 개발 역량을 발전시키고 싶다.
