> 3. **요구사항마다 완료 기준을 둔다** — 모든 세부 요구사항에 ID와 "완료 기준"이 있다. 구현 후에는 완료 기준과 9장의 정답표로 직접 확인한다.
> 4. **우선순위로 범위를 조절한다** — P1(필수) → P2(권장) → P3(선택). 시간이 부족하면 P3부터 뺀다.

## 1. 개요

### 1.1 목적

대학원 학생연구자의 **월별 지원요건 충족 여부**와 **재원별 학생지원금 지급 내역**, 그리고 지원금 재원인 **기관계정(대학계정)의 수입·지급·잔액**을 한 곳에서 조회하고, 원천 데이터와 맞는지 자동으로 검증한다.

**이 시스템이 하는 일을 순서대로 보면**

1. 매달 다른 시스템(원천)에서 학생의 학적, 지급 내역, 대학 계정 거래를 **가져온다** → "연동"
2. 가져온 학적으로 학생마다 이번 달 지원 대상인지 **판정한다** → "지원요건 O/X"
3. 지원 대상 학생이 여러 재원에서 받은 돈의 합이 최소 금액에 **모자라지 않는지** 계산한다 → "기준금액, 부족금액"
4. 가져온 데이터가 원천의 현재 값과 **여전히 맞는지** 자동으로 비교한다 → "정합성 검증"
5. 모든 변경을 기록하고, 중요한 변화가 생기면 담당자에게 **알린다** → "감사로그, 알림"

### 1.2 원천 시스템과 Mock 원천

**원천 시스템**은 데이터를 원래 가지고 있는 다른 시스템이다. 학생의 학적은 학사 시스템이, 지급 내역은 각 재원의 지급 시스템이, 대학 계정 거래는 회계 시스템이 가지고 있다. 본 시스템은 원천 데이터를 고치지 않고 **읽어서 복사해 오기만** 한다.

**Mock**은 테스트나 실습을 위해 실제 대상을 흉내 내어 만든 가짜를 말한다. 실제 동국대 시스템에는 접근할 수 없으므로, 본 시스템과 같은 DB 안에 원천 시스템 역할을 하는 테이블을 만든다. 이 테이블들은 이름이 `src_`(source, 원천)로 시작해서 본 시스템 테이블과 구분된다. 이 문서에서 "원천", "원천 데이터"는 모두 이 Mock 원천을 가리킨다.

Mock 원천 데이터는 처음에 시드 데이터(9장)로 채워지고, 이후에는 "Mock 원천 편집" 화면(SCR-13)으로만 바꾼다. 원천 값을 일부러 바꿔 보면서 연동, 불일치, 알림이 제대로 동작하는지 실습하기 위해서다.

| 원천 시스템 (Mock) | 제공 데이터 |
|---|---|
| 학적 시스템 | 지도교수 정보 / 기준월별 학생 학적정보(성명, 학위과정, 국가연구자번호, 원소속대학, 학과, 학번, 학적상태, 학기차, 지도교수, 전일제 여부, 연구활동 유형) / 월별 연구활동 이력(시스템 도입 전 과거분 포함) |
| 재원별 지급 시스템 | 학생×월×재원별 지급 건 (금액, 지급일) |
| 기관계정 회계 시스템 | 계정별 거래 내역(일자, 수입/지급, 항목, 출처, 금액, 적요) / 회계팀이 보고한 **출처(수입항목)별** 수입 총액·지급 총액·잔액 집계값 (보고 기준일까지의 누적값) |

> 회계 시스템이 "보고 집계값"을 따로 주는 이유: 원장 합계를 원장 자신과 비교하면 항상 같으므로 검증이 의미가 없다. 원천이 보고한 집계값과 비교해야 검증이 의미를 가진다.

### 1.3 사용자 역할

| 역할 | 코드 | 권한 | 우선순위 |
|---|---|---|---|
| 실무 담당자 | `ADMIN` | 모든 화면 조회, 연동 실행, 지급계획 입력, 설정 변경, 알림 수신 | P1 |
| 지도교수 | `PROF` | 본인 지도학생의 명부·지급내역만 조회 | P2 |

> P1 단계에서는 로그인 없이 `ADMIN`으로 동작해도 된다. 로그인/권한은 P2에서 붙인다.

## 2. 용어 및 공통 규칙

### 2.1 용어 사전

이 프로젝트에서만 쓰거나, 이 프로젝트에서 특별한 뜻으로 쓰는 용어다. 기술 용어(Next.js, ORM, 트랜잭션 등)는 [README의 기술 용어 사전](../README.md#g-기술-용어-사전)에 있다.

| 명부 (학적 스냅샷) | 연동으로 복사해 온 기준월별 학생 학적 목록 |
| 판정, 판정 결과 | 명부의 학적으로 R1~R4와 종합 O/X, 기한, 기준금액을 계산하는 일과 그 결과 |
| 정합성 검증, `CHK-01`~`CHK-08` | 두 데이터가 서로 맞는지 자동으로 비교하는 것. 주로 "본 시스템에 복사해 둔 값"과 "원천의 현재 값"을 비교한다. CHK = Check. 8가지가 있다 (5장) |
| 일치 / 불일치 | 정합성 검증 결과. 불일치는 대부분 "연동한 뒤에 원천이 바뀌었다"는 뜻이다 |
| 감사로그 (audit log) | 누가, 언제, 어떤 데이터를, 어떻게 바꿨는지 남기는 기록. 동작은 생성 `C`, 수정 `U`, 삭제 `D` |
| 작업자 (actor) | 감사로그에 남는 변경 주체. 사람이면 사용자 ID(`admin`), 연동이면 `SYSTEM:JOB-ACAD`처럼 Job 이름 |
| 연동 이력 | Job을 한 번 실행한 기록. 결과 상태, 읽은 건수, 성공 건수, 오류 건수, 시각 |
| 연동 오류 | 연동 중 문제가 있어 건너뛴 원천 행의 기록. 오류 코드는 `E_REQUIRED`(빈 값), `E_CODE`(없는 코드), `E_REF`(참조 대상 없음), `E_VALUE`(값 범위 오류) (4.2) |
| `SUCCESS` / `PARTIAL` / `FAILED` | 연동 결과 상태. 전부 성공 / 일부 행만 오류 / 실행 자체가 실패해 전부 취소 |
| 멱등성 | 같은 작업을 여러 번 해도 결과가 같은 성질. 원천이 그대로라면 연동을 두 번 실행해도 데이터·감사로그·알림이 늘지 않아야 한다 |
| upsert | update + insert. 같은 키의 행이 있으면 수정하고, 없으면 추가한다 |
| 알림 | 담당자에게 화면으로 보여 주는 메시지. 학적상태·요건 변경과 연동 오류 때 만들어진다 (4.3) |
| 시드 데이터 | 실습을 위해 처음에 DB에 넣어 두는 가짜 데이터. 학생 11명과 기관계정 거래 등 (9장) |
| 규칙 설정 (`rule_config`) | 기준금액, 최대지원개월 같은 업무 규칙 숫자를 저장한 테이블. 코드에 숫자를 직접 쓰지 않고 여기서 읽는다 |
| 연동 API | 스케줄러가 매월 호출하는 주소(`/api/cron/sync`). 호출되면 전월을 대상으로 세 Job을 실행한다 |

**문서 표기** — 이 문서의 번호와 기호

| 표기 | 뜻 |
|---|---|
| `SFR-001` | 기능 요구사항(Software Functional Requirement) 묶음. 원본 RFP의 번호를 그대로 쓴다. 001 명부 / 002 지급내역 / 003 기관계정 / 004 추가기능 |
| `001-04` | SFR-001의 4번째 세부 요구사항 |
| `NFR-01` | 비기능 요구사항(Non-Functional Requirement). 기능 외의 실행 환경·테스트·보안 요구 |
| `SCR-02` | 화면(Screen) 번호 (7장) |
| `S01`~`S11` | 시드 데이터의 학생 시나리오 번호 (9장) |
| P1 / P2 / P3 | 우선순위. 필수 / 권장 / 선택 |
| `[가정]` | 원본 RFP에 정해져 있지 않아 이 문서에서 임의로 정한 값 |
| `ADMIN` / `PROF` | 사용자 역할. 실무 담당자 / 지도교수 (1.3) |
| O / X | 충족 / 미충족 |
| `-` | 해당 없음 (예: 요건 X인 달의 기준금액) |

### 2.2 학기 구분 `[가정]`

| 학기 | 포함 월 | 예 |
|---|---|---|
| 1학기 | 3월 ~ 8월 | 2026-1 = 2026-03 ~ 2026-08 |
| 2학기 | 9월 ~ 다음 해 2월 | 2026-2 = 2026-09 ~ 2027-02 |

"학기 단위 조회"는 해당 학기 6개월을 한 화면에 보여 준다. 학생 1명이 한 행이고, 월별 값은 열로 펼치며, 합계 열을 둔다.

### 2.3 공통 표시 규칙

- 금액은 원 단위 정수이고, 천 단위 콤마로 표시한다.
- **미지급 월은 `0`으로 표시한다.** 빈칸이나 `-`로 표시하지 않는다. 단, 기준월에 참여학생이 아니면 `-`로 표시한다.
- 요건 충족 여부는 `O` / `X`로 표시한다.
- 정합성 검증 결과는 `일치` / `불일치` 배지로 표시하고, 불일치일 때는 클릭하면 차이 내역(항목, 본 시스템 값, 원천 값)을 보여 준다.
- 국가연구자번호(8자리)는 목록 화면에서 뒤 4자리를 마스킹한다(`20000001` → `2000****`). 상세 화면에서는 전체를 표시한다. (P2)

## 3. 업무 규칙 (가정값)

> 아래 값은 모두 **멘토링용 가정**이며 실제 제도와 다를 수 있다. 숫자는 코드에 직접 쓰지 말고 설정(규칙 설정 테이블)에서 읽어야 한다 (완료 기준에 포함).

### 3.1 지원요건 판정 `[가정]`

학생 s의 기준월 m에 대해 아래 4개를 판정한다. **종합 = R1 ∧ R2 ∧ R3 ∧ R4** 이다.

| ID | 세부요건 | 충족 조건 | 데이터 출처 |
|---|---|---|---|
| R1 | 학적상태 | 학적상태 = `재학` (휴학·수료·졸업·제적이면 X) | 학적 원천: 학적상태 |
| R2 | 전일제 | 전일제 여부 = `Y` | 학적 원천: 전일제 여부 |
| R3 | 연구활동 유형 | 연구활동 유형 ∈ {`RND`, `LAB`} (`NONE`이면 X) | 학적 원천: 연구활동 유형 |
| R4 | 지원기간 | 누적지원개월 < 과정별 최대지원개월 | 학적 원천: 연구활동 이력 |

**연구활동 유형 코드**

| 코드 | 의미 |
|---|---|
| `RND` | 국가 R&D 과제 참여 |
| `LAB` | 연구실 자체 연구 |
| `NONE` | 연구활동 없음 |

**R4 계산**

- 누적지원개월 = 연구활동 이력에서 기준월 **이전** 월 중 활동유형이 `RND` 또는 `LAB`인 월의 수
- 과정별 최대지원개월: 석사 `24`, 박사 `48`, 석박통합 `72`
- 향후 최대 지원가능 기한 = 기준월 + (최대지원개월 − 누적지원개월 − 1)개월. R4가 O일 때만 표시하고, X이면 `기한 만료`로 표시한다.
  - 예: 석사, 기준월 2026-03, 누적 20 → 기한 = 2026-03 + 3개월 = **2026-06**

### 3.2 기준금액 `[가정]`

| 학위과정 | 조건 | 월 기준금액 |
|---|---|---|
| 석사 | — | 800,000원 |
| 박사 | — | 1,100,000원 |
| 석박통합 | 학기차 ≤ 4 | 800,000원 |
| 석박통합 | 학기차 ≥ 5 | 1,100,000원 |

- 기준금액은 **종합 요건이 `O`인 월에만** 적용한다. `X`인 월은 기준금액·충족여부·부족금액을 모두 `-`로 표시한다.
- 기준금액 충족 여부 = 총지급액 ≥ 기준금액
- 부족금액 = max(0, 기준금액 − 총지급액)

### 3.3 재원 코드

| 코드 | 대분류 | 재원명 |
|---|---|---|
| `F11` | 통합관리 | 대학계정 |
| `F12` | 통합관리 | 기관 세부계정 |
| `F13` | 통합관리 | 연구책임자계정 |
| `F20` | 비통합관리 R&D | 정부·지자체·민간 R&D |
| `F30` | BK21 | BK21 장학금 |
| `F40` | 국고·지자체 | 그 외 국고·지자체 지원 |
| `F90` | 기타 | 기타 |

### 3.4 기관계정 항목 코드

| 코드 | 구분 | 항목명 |
|---|---|---|
| `I_CARRY` | 수입 | 전년도 잔액(이월). 매년 1월 1일 거래로 기록 |
| `I_GOV` | 수입 | 이공계 연구생활장려금(정부 지원) |
| `I_UNIV` | 수입 | 대학 자체예산 |
| `I_PI` | 수입 | 연구책임자계정에서의 기관계정 대체액 |
| `I_EXTRA` | 수입 | 추가기여금 |
| `I_REPAY` | 수입 | 상환금 |
| `I_INT` | 수입 | 발생이자 |
| `O_PAY` | 지급 | 학생인건비 지급 |
| `O_ETC` | 지급 | 기타 지급 |

- **수입 총액 = 전년도 잔액(`I_CARRY`) + 대상연도 수입액(`I_GOV`~`I_REPAY`) + 이자수익(`I_INT`)**
- 출처별 잔액은 **재원 출처(수입 항목) 단위**로 관리한다. 지급 거래는 반드시 어느 출처에서 나갔는지를 가진다.
  - 예: `O_PAY` 100만 원, 출처 `I_GOV` → I_GOV 출처의 잔액이 100만 원 줄어듦

## 4. 원천 연동 요구사항

### 4.1 연동 작업

연동 작업(Job)은 3종류다. 각각 원천 시스템 하나를 맡는다.

| 이름 | 코드 | 원천 → 본 시스템 | 처리 |
|---|---|---|---|
| 학적 연동 | `JOB-ACAD` | 학적 시스템 → 명부 | 기준월 단위로 지도교수·학적을 명부에 반영(있으면 수정, 없으면 추가) → 누적지원개월 계산 → **지원요건 판정 재실행** → 변경 감지 알림 |
| 지급 연동 | `JOB-PAY` | 재원별 지급 시스템 → 지급내역 | 기준월 단위로 원천과 똑같이 맞춤 (원천에 없는 행은 삭제) |
| 기관계정 연동 | `JOB-ACCT` | 기관계정 회계 시스템 → 기관계정 원장 | 기간 단위로 거래 내역을 원천과 똑같이 맞춤 |

### 4.2 공통 동작

- **실행 방법**: ① 연동관리 화면에서 Job과 기준월(또는 기간)을 골라 수동 실행, ② **매월 1회** 스케줄 자동 실행 (전월 대상). 원본의 "최소 월 1회 연동"은 ②로 충족한다. 본 시스템은 스케줄러가 호출할 **연동 API**(`/api/cron/sync`, 전월 대상으로 세 Job 실행)를 제공한다. 이 API를 매월 호출하도록 스케줄러에 등록하는 일은 호스팅 환경에 따라 다르므로 이 실습 범위 밖이다.
- **실행 순서**: 같은 기준월이라면 **JOB-ACAD를 먼저** 실행해야 한다. JOB-PAY는 학번이 그 월의 명부에 있는지 확인하기 때문이다(`E_REF`). 스케줄 실행은 JOB-ACAD → JOB-PAY → JOB-ACCT 순서로 한다.
- **멱등성**: 같은 대상으로 여러 번 실행해도 결과가 같아야 한다. 원천과 값이 같은 행은 **쓰지 않고 감사로그도 남기지 않는다.** 따라서 원천이 바뀌지 않은 상태에서 다시 실행하면 감사로그가 늘지 않는다. 단, 연동 시각(`synced_at`)과 판정 시각(`judged_at`)은 비교 대상에서 뺀다.
- **삭제**: 대상 기준월(또는 기간)의 본 시스템 데이터 중, 이번 연동에서 **정상 처리된 원천 행에 없는 행**은 삭제한다(감사로그 `D`). 원천에서 사라진 행과 오류가 난 행이 모두 여기에 해당한다. 명부 행을 삭제할 때는 같은 학생·월의 판정 결과도 함께 삭제한다.
- **감사로그**: 연동 중에 생긴 생성·수정·삭제는 모두 감사로그에 기록하고, 작업자는 `SYSTEM:JOB-ACAD`처럼 남긴다.
- **오류 처리**: 아래 오류가 난 행은 건너뛰고 연동 오류로 기록한다. 나머지 행은 계속 처리한다. 한 행에 오류가 여러 개면 **표의 위에 있는 오류 하나만** 기록한다.

| 오류 코드 | 조건 |
|---|---|
| `E_REQUIRED` | 필수 값이 비어 있음 |
| `E_CODE` | 정의되지 않은 코드 |
| `E_REF` | 참조 대상 없음 |
| `E_VALUE` | 값 범위 오류 |

**Job별 검증 항목**

| Job | `E_REQUIRED` 대상 | `E_CODE` 대상 | `E_REF` 대상 | `E_VALUE` 대상 |
|---|---|---|---|---|
| JOB-ACAD (지도교수) | 교수ID, 성명, 국가연구자번호, 학과 | — | — | — |
| JOB-ACAD (학적) | 학번, 성명, 학위과정, 국가연구자번호, 원소속대학, 학과, 학적상태, 학기차, 지도교수, 전일제, 활동유형 | 학위과정(`석사`/`박사`/`석박통합`), 학적상태(`재학`/`휴학`/`수료`/`졸업`/`제적`), 전일제(`Y`/`N`), 활동유형(`RND`/`LAB`/`NONE`) | 지도교수가 지도교수 원천에 없음 | 학기차 < 1 |
| JOB-PAY | 학번, 재원코드, 금액, 지급일 | 재원코드(3.3의 7개) | 학번이 같은 기준월 명부에 없음 | 금액 < 0, 지급일이 `YYYY-MM-DD` 형식이 아님 |
| JOB-ACCT | 계정, 거래일자, 구분, 항목, 출처, 금액 | 구분(`IN`/`OUT`), 항목(3.4), 출처(3.4의 수입항목 `I_*`) | 계정이 기관계정 마스터에 없음 | 금액 ≤ 0, 수입(`IN`)인데 출처 ≠ 항목 |

- **결과 상태**: 오류 0건이면 `SUCCESS`, 일부 오류면 `PARTIAL`, 예외로 중단되면 `FAILED`(전체 롤백). 실행마다 상태, 읽은 건수, 성공 건수, 오류 건수, 시작·종료 시각, 실행 방식(수동/스케줄)을 기록한다. 읽은 건수는 JOB-ACAD는 학적 행, JOB-PAY는 지급 행, JOB-ACCT는 거래 행 기준으로 센다. `PARTIAL`/`FAILED`이면 ADMIN에게 `SYNC_ALERT` 알림을 만든다.

### 4.3 변경 감지 알림 (JOB-ACAD 후처리)

판정을 다시 실행한 뒤, 같은 학생의 **직전 값**과 비교한다. 직전 값은 같은 기준월에 이미 저장된 값이 있으면 그 값이고, 없으면 전월 값이다. **둘 다 없으면 알림을 만들지 않는다** (예: 처음 연동하는 월).

| 알림 유형 | 조건 |
|---|---|
| `ACAD_STATUS_CHANGED` | 학적상태 변경 (예: 재학 → 휴학) |
| `REQ_DETAIL_CHANGED` | R1~R4 중 하나라도 변경 |
| `ELIGIBILITY_CHANGED` | 종합 O/X 변경 |

알림 본문에는 학생명, 학번, 기준월, 변경 전/후 값을 넣고, 링크를 누르면 학생 상세 화면으로 이동한다.

## 5. 정합성 검증 규칙

검증은 **화면을 조회할 때 계산**하는 방식을 기본으로 한다. 정합성 점검 화면(SCR-09)에서는 전체를 한 번에 실행해 결과를 표로 보여 준다.

| ID | 검증 내용 | 비교 A (본 시스템) | 비교 B | 단위 |
|---|---|---|---|---|
| `CHK-01` | 학적정보 원천 일치 | 학적 스냅샷의 학적 항목 | 학적 원천의 현재 값 | 학생×월 |
| `CHK-02` | 종합결과 = 세부요건 종합 | 저장된 종합 O/X | R1∧R2∧R3∧R4 | 학생×월 |
| `CHK-03` | 세부요건 원천 일치 | 저장된 R1~R4 | 원천 현재 값으로 **다시 판정한** R1~R4 | 학생×월 |
| `CHK-04` | 재원별 합계 = 총지급액 | 재원별 지급액의 합 | 화면에 표시한 총지급액 | 학생×월 |
| `CHK-05` | 재원별 지급내역 원천 일치 | 지급내역 (학생·월·재원별 합계) | 재원 원천의 같은 키 합계 | 학생×월×재원 |
| `CHK-06` | 항목별 세부내역 합계 = 항목별 총액 | 원장의 항목별 수입/지급 합계 | 회계 보고 집계의 수입/지급 총액 | 계정×항목 |
| `CHK-07` | 항목별 (수입 − 지급) = 잔액 | 원장의 출처별 수입 − 지급 | 회계 보고 집계의 잔액 | 계정×항목 |
| `CHK-08` | 수입총액 − 지급총액 = 잔액총액 | 원장 전체 수입 − 지급 | 회계 보고 잔액의 합 | 계정 |

**세부 기준**

- **CHK-01 비교 항목**: 성명, 학위과정, 국가연구자번호, 원소속대학, 학과, 학적상태, 학기차, 지도교수, 전일제, 활동유형. 원천에 해당 학생·월 행이 없으면 `불일치(원천에 없음)`로 표시한다.
- **CHK-03**: 원천의 현재 학적값과 현재 연구활동 이력으로 누적지원개월을 다시 계산하고, 3.1 규칙으로 R1~R4를 다시 판정해 비교한다.
- **CHK-04**: 정상이면 항상 일치한다. 재원별 금액과 총액을 서로 다른 경로로 계산했을 때 생기는 버그를 잡기 위한 검증이다. 총액은 SQL `SUM`으로, 재원별 합계는 화면에 표시하는 재원별 값을 더해서 비교한다.
- **CHK-05**: 원천은 학번이 비어 있지 않은 **모든 행**을 대상으로 한다. 연동 오류로 반영되지 않은 행도 포함하므로, 원천에만 있는 금액은 `불일치(본 시스템에 없음)`로 표시된다.
- **CHK-06~08**: 회계 보고 집계는 보고 기준일(`base_date`)까지의 누적값이다. 따라서 화면의 조회 기간과 상관없이, 원장의 **보고 기준일까지의 누적 거래**로 계산해 비교한다. 계정에 보고 집계가 여러 기준일로 있으면 가장 최근 기준일을 쓴다.

> 불일치는 "연동 이후 원천 값이 바뀌었을 때" 생긴다. 실습할 때는 SCR-13에서 원천 값을 바꾼 뒤, 연동 전에는 `불일치`로, 연동 후에는 `일치`로 바뀌는지 확인한다.

- 원본의 보안서약, 취약점 진단, 정보보안시스템 연계는 범위에서 뺀다.
